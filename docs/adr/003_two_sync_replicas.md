# ADR 003: Подтверждение записи двумя синхронными репликами

## Статус

Принято.

## Контекст

Для платформы краткосрочной аренды жилья потеря подтвержденной записи недопустима. Если клиент получил успешный ответ на создание бронирования или платежа, эти данные должны сохраниться даже при отказе основного узла PostgreSQL.

Обычная асинхронная репликация не дает такой гарантии: основной узел может подтвердить транзакцию клиенту до того, как изменения попадут на реплику. При аварии это создает риск потери уже подтвержденных данных.

## Решение

Настроить строгий режим записи: транзакция считается подтвержденной только после фиксации на основном узле и получения подтверждения минимум от двух синхронных реплик.

Целевая гарантия проекта:

```text
RPO = 0 для подтвержденных транзакций
```

Это означает, что уже подтвержденные записи не теряются при отказе основного узла, если в момент подтверждения были доступны две синхронные реплики.

## Обоснование

Выбор двух синхронных реплик усиливает защиту данных по сравнению с режимом, где достаточно одной реплики:

- при отказе основного узла подтвержденная транзакция остается минимум на двух других узлах;
- кластер может выбрать новый основной узел из реплик, уже содержащих подтвержденные данные;
- демонстрация ясно показывает компромисс между сохранностью данных и доступностью записи.

Такой режим соответствует учебной цели проекта: показать, что высокая доступность не сводится к автоматическому переключению, а включает осознанный выбор гарантий записи.

## Последствия

- Если доступны основной узел и две подходящие синхронные реплики, запись работает штатно.
- Если одна синхронная реплика отказала, Patroni может перестроить набор синхронных реплик при наличии подходящей замены.
- Если двух синхронных реплик больше нет, новая запись должна остановиться.
- Остановка записи в этом случае является защитным поведением, а не ошибкой архитектуры.
- Цена решения - более высокая задержка записи и меньшая доступность записи при деградации кластера.

## Границы решения

`RPO = 0` относится только к подтвержденным транзакциям и только к техническим отказам узлов. Это не защита от логических ошибок приложения, ручных ошибочных SQL-команд или неудачных миграций. Для таких случаев нужны резервные копии, архив WAL и восстановление на момент времени.
