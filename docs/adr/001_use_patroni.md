# ADR 001: Patroni как средство управления PostgreSQL-кластером

## Статус

Принято.

## Контекст

Проект демонстрирует базу данных как отказоустойчивую систему, а не как один отдельно запущенный сервер PostgreSQL. Для этого недостаточно настроить потоковую репликацию: кластеру нужен компонент, который отслеживает состояние узлов, определяет текущий основной узел и безопасно выполняет переключение при отказе.

В учебном стенде важно, чтобы этот процесс был наблюдаемым и объяснимым на защите. Решение должно показывать, почему запись идет только на один основной узел, как выбирается новый основной узел и почему маршрутизатор может доверять текущему состоянию кластера.

## Решение

Использовать Patroni для управления PostgreSQL-кластером.

Patroni отвечает за:

- запуск PostgreSQL-узла в нужной роли;
- регистрацию состояния узла в согласованном хранилище;
- удержание права основного узла;
- автоматическое переключение при отказе;
- предоставление HTTP-проверок состояния для HAProxy.

В качестве согласованного хранилища состояния используется etcd. Его топология зафиксирована в отдельном решении ADR 002.

## Обоснование

Patroni хорошо подходит для цели проекта, потому что явно показывает ключевые механизмы высокой доступности PostgreSQL:

- у кластера есть только один узел, принимающий запись;
- право на запись связано с состоянием в etcd;
- отказ основного узла приводит к управляемому выбору нового основного узла;
- HAProxy может выбирать маршрут записи и чтения на основе HTTP-проверок Patroni.

Это решение делает демонстрацию понятнее, чем вариант с полностью скрытым управляемым сервисом: на защите можно показать состояние узлов, переключение роли и поведение маршрутизации.

## Последствия

- В архитектуре появляется отдельный контур согласования состояния.
- Для корректной работы кластера нужно контролировать не только PostgreSQL, но и доступность etcd.
- Потеря кворума etcd ограничивает возможность безопасно выбирать новый основной узел.
- Переключение и маршрутизация записи должны опираться на состояние Patroni, а не только на факт доступности процесса PostgreSQL.

## Границы решения

Patroni не заменяет резервное копирование и не защищает от логических ошибок в данных. Ошибочный `UPDATE`, `DELETE`, `DROP` или неудачная миграция будут воспроизведены репликацией. Для таких сценариев используется pgBackRest, архив WAL и восстановление на момент времени.
