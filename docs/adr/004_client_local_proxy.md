# ADR 004: Отдельная цепочка PgBouncer и HAProxy для каждого клиента

## Статус

Принято.

## Контекст

Клиентский доступ к PostgreSQL-кластеру должен сохраняться при отказе отдельного прокси-компонента. Если все клиенты подключаются через один общий PgBouncer или один общий HAProxy, этот компонент становится единой точкой отказа для всего стенда.

В проекте нужно показать более устойчивую схему подключения, близкую к промышленной практике: каждый клиентский контур имеет собственную точку входа, а общий кластер PostgreSQL остается единым.

## Решение

Для каждого демонстрационного клиента используется отдельная цепочка подключения:

```text
client-a -> PgBouncer клиента A -> HAProxy клиента A -> PostgreSQL/Patroni
client-b -> PgBouncer клиента B -> HAProxy клиента B -> PostgreSQL/Patroni
```

Общий HAProxy перед всеми клиентами не используется. В стенде поднимаются два HAProxy с одинаковыми правилами маршрутизации, но с независимыми контейнерами и портами.

## Обоснование

Разделение клиентских цепочек позволяет показать, что отказ прокси у одного клиента не обязан нарушать работу другого клиента.

PgBouncer решает задачу управления соединениями:

- держит пул соединений ближе к клиенту;
- уменьшает стоимость открытия соединений к PostgreSQL;
- разделяет логические подключения для записи, чтения и служебных операций.

HAProxy решает задачу маршрутизации:

- отправляет запись на текущий основной узел;
- отправляет обычное чтение на доступные реплики;
- проверяет состояние PostgreSQL-узлов через HTTP-интерфейс Patroni;
- после переключения основного узла перенаправляет новые соединения на актуальный узел.

Такое разделение делает архитектуру читаемой: PgBouncer отвечает за соединения, HAProxy - за выбор живого и подходящего PostgreSQL-узла.

## Последствия

- В системе появляется несколько независимых клиентских цепочек подключения.
- Отказ PgBouncer или HAProxy в одной клиентской цепочке не должен блокировать остальные клиентские цепочки.
- Мигратор использует служебный маршрут записи через `haproxy-client-a`, но не проходит через PgBouncer.
- После переключения основного узла старые соединения могут потребовать переоткрытия, поэтому клиентские пулы должны поддерживать reconnect.
- Клиент должен явно выбирать режим чтения: обычное чтение с реплик или строгое чтение через маршрут записи.

## Границы решения

Схема с двумя клиентскими цепочками демонстрирует устранение единой точки отказа на уровне прокси в рамках учебного стенда. В промышленной системе дополнительно потребуются балансировка перед клиентскими точками входа, сетевые политики, TLS, управление секретами и мониторинг каждого прокси.
