# ADR 004: клиентские PgBouncer и HAProxy

## Решение

Для каждого демонстрационного клиента используется отдельная цепочка подключения:

```text
client-a -> PgBouncer A -> HAProxy A -> PostgreSQL/Patroni
client-b -> PgBouncer B -> HAProxy B -> PostgreSQL/Patroni
```

## Обоснование

Отказ прокси одного клиента не должен ломать доступ другого клиента к кластеру. Поэтому PgBouncer и HAProxy располагаются на стороне конкретного клиента, а не как один общий прокси-компонент перед всей базой.

PgBouncer отвечает за пул соединений и выбор логического подключения: `rental_write`, `rental_read` или `rental_migration`. HAProxy отвечает за маршрутизацию к текущему основному узлу или к доступным репликам по данным Patroni REST API.

## Последствия

- В стенде становится два HAProxy с одинаковой конфигурацией маршрутов.
- Мигратор использует `haproxy-client-a` как служебный маршрут записи.
- После failover нужно учитывать переоткрытие соединений PgBouncer.
- Клиент должен явно выбирать обычный или строгий режим чтения.
