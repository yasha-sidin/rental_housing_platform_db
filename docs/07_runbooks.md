# Операционные инструкции

Операционные инструкции фиксируют порядок проверки и восстановления ключевых свойств кластера: доступности записи, сохранности подтвержденных транзакций, независимости клиентских цепочек и пригодности резервных копий.

![Сценарии отказа PostgreSQL-кластера высокой доступности](diagrams/png/06_failure_scenarios.png)

## Отказ основного узла

1. Зафиксировать текущее состояние контейнеров командой `docker compose ps`.
2. Определить текущий основной узел через Patroni REST API или SQL-функцию `pg_is_in_recovery()`.
3. Остановить контейнер текущего основного узла.
4. Дождаться повышения одной из реплик до роли основного узла.
5. Проверить, что маршрут записи HAProxy указывает на новый основной узел.
6. Выполнить контрольную запись.
7. Сохранить диагностический вывод в `demo/03-failover/artifacts/`.

## Потеря синхронных реплик

1. Остановить одну синхронную реплику и проверить, что запись остается доступной.
2. Остановить вторую синхронную реплику, необходимую для подтверждения записи.
3. Зафиксировать остановку записи из-за недостатка синхронных подтверждений.
4. Объяснить связь этого поведения с `RPO = 0` (`Recovery Point Objective`, целевая точка восстановления; в проекте - допустимая потеря данных при аварии).
5. Сохранить диагностический вывод в `demo/05-sync-rpo-zero/artifacts/`.

## Отказ локальной клиентской цепочки

1. Остановить `pgbouncer-client-a` или `haproxy-client-a`.
2. Зафиксировать недоступность клиента A через его собственную цепочку подключения.
3. Проверить, что клиент B продолжает выполнять SQL через `pgbouncer-client-b` и `haproxy-client-b`.
4. Сохранить диагностический вывод в `demo/04-proxy-failure/artifacts/`.

## Логическая ошибка

1. Подготовить полную резервную копию и убедиться в наличии архива WAL.
2. Создать контрольную строку для последующей проверки восстановления.
3. Зафиксировать точку восстановления или временную метку до логической ошибки.
4. Выполнить ошибочный `DELETE`.
5. Проверить, что логическая ошибка воспроизведена на рабочем кластере.
6. Восстановить отдельный восстановительный узел на момент до ошибки.
7. Сохранить проверочный SQL-запрос в `demo/07-pitr/artifacts/`.

## Деградация рабочего контейнера резервного копирования

1. Остановить активный рабочий контейнер резервного копирования.
2. Запустить резервное копирование вторым рабочим контейнером.
3. Проверить состояние репозитория резервных копий.
4. Сохранить вывод `pgbackrest info` и `pgbackrest check`.
