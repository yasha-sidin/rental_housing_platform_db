# Проектирование схемы базы данных

## Миграции

Цепочка миграций компактная и читаемая:

```text
V001__database_baseline.sql
V002__reference_catalogs.sql
V003__users_listings_photos.sql
V004__pricing_availability.sql
V005__bookings_payments_reviews.sql
V006__indexes_comments_grants.sql
```

## Принципы

- В первой миграции создается прикладная схема `application`.
- В миграциях создаются два уровня ролей: PostgreSQL-роли для доступа к объектам схемы и доменные роли для прикладных полномочий.
- Все таблицы, ограничения, индексы, комментарии и права доступа создаются внутри схемы `application`.
- Индексы и комментарии сгруппированы в отдельной миграции.
- Rollback-файлы парные и соответствуют up-миграциям.

## Роли и права доступа

В проекте слово "роль" используется в двух разных смыслах.

Первый уровень - PostgreSQL-роли, которые управляют доступом к объектам базы данных. Они создаются в `V001__database_baseline.sql`:

- `app_readonly` получает чтение таблиц и последовательностей;
- `app_readwrite` наследует `app_readonly` и получает права на запись;
- `app_owner` наследует `app_readwrite`, владеет объектами схемы и получает административные права на функции, типы, таблицы и последовательности.

Иерархия задается через `GRANT app_readonly TO app_readwrite` и `GRANT app_readwrite TO app_owner`. В `V006__indexes_comments_grants.sql` эти роли получают права на уже созданные объекты и права по умолчанию для будущих объектов схемы `application`.

Второй уровень - доменные роли прикладной модели. Они создаются в `V002__reference_catalogs.sql`: `guest`, `owner`, `admin`. Там же создаются атомарные права в `permissions` и связи `role_permissions`.

Доменные роли не взаимоисключающие. Связующая таблица `user_roles` создается в `V003__users_listings_photos.sql` и позволяет одному пользователю иметь несколько ролей одновременно. Это отражает предметную область: один и тот же человек может бронировать жилье как гость, публиковать собственные объекты как владелец и при необходимости иметь административные полномочия.

## Группы таблиц

Схема устроена слоями:

- справочный слой: `countries`, `cities`, `object_types`, `currencies`;
- пользовательский слой: `users`, `roles`, `permissions`, `user_roles`, `role_permissions`;
- слой каталога жилья: `addresses`, `listings`, `photos`, `listing_photos`;
- слой цен и календаря: `base_prices`, `listing_availability_days`, `price_history`;
- слой проживания и расчетов: `bookings`, `booking_days`, `payments`, `reviews`.

Такой порядок отражен в миграциях: сначала создаются типы, роли и базовая схема, затем справочники, пользователи, объявления, календарь доступности, бронирования, платежи, отзывы, индексы, комментарии и права доступа.

## Индексы

Индексы создаются под конкретные сценарии доступа:

| Индекс | Тип сценария | Назначение |
| --- | --- | --- |
| `idx_listings_owner_id` | Операционный | Быстрый вывод объявлений конкретного владельца. |
| `idx_listings_description_fts` | Поиск | Полнотекстовый поиск по описанию объявления через GIN-индекс. |
| `idx_listings_active_capacity_rooms` | Поиск | Выбор активных объявлений по вместимости и числу комнат; скрытые и заблокированные объявления не попадают в индекс. |
| `idx_addresses_city_id_postal_code` | Справочный поиск | Поиск адреса внутри города по нормализованному почтовому индексу. |
| `idx_bookings_created_by_user_creation_date_desc` | История пользователя | Чтение бронирований пользователя от новых к старым. |
| `idx_payments_status_session_expires_at` | Операционное обслуживание | Поиск платежных сессий по статусу и сроку истечения. |
| `idx_reviews_unmoderated_creation_date` | Модерация | Очередь немодерированных отзывов по времени создания. |

Планы выполнения для ключевых индексов сохранены в `scenarios/analytical/04-index-plan-analysis/`. В них видны `Index Scan`, `Bitmap Index Scan` и `Index Only Scan` для запросов, где селективность данных делает индекс полезным.

## Данные

Seed-данные разделены по смыслу:

```text
001_reference.sql
002_demo_users_listings.sql
003_booking_scenarios.sql
004_pitr_scenario.sql
999_cleanup.sql
```

Массовая генерация данных вынесена в команду `bin/rentalctl seedgen` (`bin/rentalctl.exe seedgen` на Windows). Генератор написан на Go и создает SQL на лету, чтобы в репозитории не хранить большой нечитаемый seed-скрипт.

## Проверки

SQL-проверки находятся в `db/tests/`. Они фиксируют не весь набор тестов, а ключевые инварианты схемы: непротиворечивость бронирований, платежей, отзывов, календаря доступности и цен.

Дополнительные проверочные сценарии находятся в `scenarios/`. Они разделены на операционные и аналитические. Каждый сценарий содержит SQL-запрос и артефакт результата: снимок выполнения, CSV-выгрузку или план `EXPLAIN (ANALYZE, BUFFERS)`. Эти материалы нужны для проверки того, что схема поддерживает реальные действия прикладного слоя и аналитические выборки.
